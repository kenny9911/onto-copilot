# 决策与变更影响
> 将已记录决策校验为带基线、前置条件、影响范围和回滚线索的变更提案

## 何时用
问题已有明确回答或决策记录，需判断其是否适用于当前基线、会影响哪些产物，
并生成可审核的 patch 提案时使用；没有明确决策记录时不用本技能猜测用户意图

## 步骤
1. 只接受带决策 ID、当前状态、回答原文、决策人或角色、时间和基线 revision
   的记录。讨论、建议、未回答问题和模型推断不是已决策。
2. 用 `evidence.search` 和 `evidence.rows` 核对决策依据与适用范围；决策人权限、组织、
   版本或时间不明时标为待解决，不产生变更。
3. 用 `oir.query` 确认所有 target ID 和 before 状态来自当前基线；用 `model.lint`
   读取已有确定性错误，不用 patch 提案掩盖基线本身的无效状态。
4. 将决策分为 `APPLICABLE`、`NO_CHANGE`、`AMBIGUOUS`、`STALE` 或 `CONFLICTING`。
   只有 APPLICABLE 且可定位目标时才生成 patch 提案。
5. 对每个候选变更运行 `impact.trace`，必要时用 `entity.compare` 验证涉及合并或身份
   变更的对象；记录直接与间接下游、不可逆性和共享依赖。
6. 每条 patch 提案写明 base revision、decision ID、操作、target ID/路径、before/after
   摘要、前置条件、影响 ID、风险和证据。提案不是已执行变更。
7. 新决策与历史决策冲突时保留两条记录，只有明确 supersedes 关系时才标记取代；
   否则形成 unresolved item，不按时间新旧自动选择。
8. 影响或前置条件不完整时停在提案阶段，给出应答角色、被阻塞产物和所需证据；
   不调用写工具，不声称已落地、已发布或已签字。

## 完成判据
- 每条评估都关联决策 ID 和当前 base revision
- 未记录的建议、讨论和推断没有被当成决策
- 只有 APPLICABLE 决策生成 patch 提案，其余均保留可追溯原因
- 每条 patch 提案包含前后摘要、前置条件、影响 ID、风险和证据
- 冲突决策未被静默覆盖，supersedes 关系有明确依据
- 输出只是 patch 提案，没有声称已修改、已发布或已获人工签字

## 工具
evidence.search、evidence.rows、oir.query、impact.trace、entity.compare、model.lint

## 标签
决策集成、变更影响、patch、revision、supersede
