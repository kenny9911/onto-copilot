# 验收测试与追溯
> 将需求、规则、流程、集成和决策转成可执行测试设计与双向覆盖，不伪造执行结果

## 何时用
需求或候选方案已有稳定 ID，需定义 UAT、业务规则、集成、数据质量、授权或 SoD 验收测试，
并检查覆盖缺口时使用；没有实际运行记录时不宣称测试通过

## 步骤
1. 冻结本轮输入基线：requirement、Rule、process step、integration contract、决策和已知
   限制的 ID/版本。未确认候选与已确认需求分开标记。
2. 用 `oir.query` 校验所有引用，用 `model.lint` 先处理缺 ID、悬空引用、无效枚举和
   不可达流程等确定性问题；输入未定稿时测试只能为 BLOCKED/DRAFT。
3. 每个测试只验收一个主要结果，用 Given/When/Then 写明前置、输入、触发和可观察
   预期；“系统正常”、“结果正确”不是可验收预期。
4. 为规则和计算覆盖正例、边界、反例和例外；为流程覆盖主路径、异常、超时、取消
   和人工介入；为集成覆盖重复、乱序、部分失败、重试、对账和权限失败。
5. 用 `evidence.search` 和 `evidence.rows` 核验阈值、单位、期望结果、测试数据来源与责任人；
   缺少依据时形成 coverage gap，不自行编造阈值或敏感数据。
6. 建立 requirement → test case 和 test case → requirement/Rule/step/contract 的双向追溯；
   将覆盖分为 `COVERED`、`PARTIAL`、`UNCOVERED` 或 `BLOCKED`。
7. 用 `impact.trace` 检查需求或方案变更应回归哪些测试；测试的 automation candidate 只是
   自动化可行性建议，不代表脚本已实现。
8. 只在没有 blocking coverage gap 且所有必要测试设计可审查时建议
   `READY_FOR_HUMAN_REVIEW`；该建议不是测试通过、业务验收或人工签字。

## 完成判据
- 每个测试只验收一个主要结果，Given/When/Then 可观察
- 规则的正例、边界、反例和适用例外已覆盖或已形成缺口
- 流程异常与集成失败语义已覆盖或已形成缺口
- 需求与测试之间存在双向追溯，覆盖状态使用合法枚举
- 阈值、期望结果和测试数据要求没有被无证据编造
- readiness 只表示测试设计可交人工评审，没有声称已执行、已通过或已签字

evidence.search、evidence.rows、oir.query、impact.trace、model.lint
