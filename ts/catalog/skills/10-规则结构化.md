# 规则结构化
> 将政策、控制和专家口径转成类型明确、边界完整、可追溯且可用正反例验收的原子规则

## 何时用
材料或访谈出现必须、不得、只有、超过、在某期限内、按公式计算、需要审批或满足
条件后执行等可判定约束时使用；愿景、原则和无法观察结果的目标不作为规则

## 步骤
1. 先按当前 schema 将规则归为 `VALIDATION`、`PROCESS`、`AUTHORITY`、
   `CALCULATION` 或 `DERIVATION`。把复合句拆成原子规则，每条只有一个可判定 effect。
2. 为每条规则记录稳定 ID、kind、触发 Event、适用对象 ID、condition、effect、
   exceptions 和 evidence IDs。材料未明确绑定对象或事件时保留 schema 允许的空值
   并提问，不猜 ID。
3. condition 必须写清变量、类型、单位、时间点、时区、统计窗口、空值处理和边界
   运算符；“超过 1000”不得被改写成“大于等于 1000”。
4. 计算规则在 condition/effect 中明确公式、舍入、汇率来源和结果单位；时限规则
   区分自然日与工作日；状态规则写明前置和后置状态。
5. 用决策表检查重叠、遗漏、冲突和优先级。法规、集团、地区和本地规则分别保留
   来源层级、生效期和例外，不自行覆盖。
6. 用 `oir.query` 和 `impact.trace` 检查 Rule 与 Action、Event、DataObject 和
   流程步骤的引用。当前 schema 无法承载的优先级、生效期或规则层级写入
   `questions` 或 `conflicts` 字符串，不新增规则字段。
7. 每条规则至少生成 `POSITIVE`、`BOUNDARY`、`NEGATIVE` 和适用时的 `EXCEPTION`
   用例；given 使用现有字段，expected 必须可判断。测试失败时修正规则表达，不修改
   证据原文。
8. questions 只支持字符串时按 `[应答角色][rule:ID] 问题 | expected:格式 |
   evidence:ID` 编码，保留路由所需信息。

## 完成判据
- 每条规则只有一个可判定 effect，且 kind 使用合法枚举
- 变量类型、单位、时间语义、空值和边界运算符已明确
- trigger、applies-to、condition、effect、exceptions 和证据可追溯
- 冲突、优先级和生效期没有被静默覆盖，无法承载的内容已进入 questions/conflicts
- 正例、边界、反例和适用的例外均有验收用例
- 不可判定目标和缺证据绑定已进入 questions
- 输出没有添加 schema 未定义字段
