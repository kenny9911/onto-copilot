# 数据对象治理
> 治理 DataObject 的业务身份、生命周期、权威源、质量控制和敏感性，而不是机械复制数据库表

## 何时用
流程已经识别输入输出，但 DataObject 的分类、业务键、生命周期、System of Record、
责任人、质量规则或敏感性仍缺失时使用；纯物理表结构抽取不等同于本技能

## 步骤
1. 用 `entity.compare` 和 `oir.query` 区分业务对象、单据、主数据、事务数据、
   派生数据及其物理表示。一个表可能承载多个概念，一个概念也可能跨多个表。
2. 为每个对象记录稳定 ID、业务名称、classification、业务键、技术键区别、生命周期
   状态和证据。当前 classification 没有 `UNKNOWN` 枚举：证据不足的对象不要猜分类，
   将对象 ID 和所需证据写入 questions。
3. 标明 System of Record、数据负责人和 lifecycle states。复制或消费系统、同步方向、
   新鲜度等当前 schema 无法承载的信息，若影响决策则形成 question，不新增对象字段。
   System of Record 不等于数据最早出现的系统，也不等于报表库。
4. 用 `profile.column` 验证完整性、唯一性、有效性、一致性和及时性候选；样本分布
   不能代替业务规则证据。
5. 质量规则必须包含 data object ID、合法 dimension、可执行 expression、数值 threshold
   及证据。没有有依据的数值阈值时不生成该规则，改为 question，不编造 threshold。
6. 敏感性使用 `PUBLIC`、`INTERNAL`、`CONFIDENTIAL`、`RESTRICTED` 或 `UNKNOWN`，
   依据客户政策而非字段名常识。最小访问、脱敏、保留、删除、驻留和 legal hold
   当前无专用字段，写入 questions，不塞进无关字段。
7. 用 `impact.trace` 检查对象变化对流程、规则、ERP mapping、消费者和质量规则的
   影响；高风险合并或分类变更需要决策问题。
8. 用 `model.lint` 检查稳定 ID、引用、重复键和非法状态。questions 只支持字符串时
   按 `[应答角色][object:ID] 问题 | expected:格式 | evidence:ID` 编码。

## 完成判据
- DataObject 没有按数据库表一对一机械生成
- 业务键、技术键、生命周期和 System of Record 已区分
- classification 有证据；无法分类的对象未被猜测并已形成问题
- owner 和 sensitivity 有证据、schema 允许的空值或 UNKNOWN
- 每条质量规则都有可执行表达式和有依据的数值阈值
- 访问、脱敏、保留和驻留要求已进入 questions，未塞入 schema 外字段
- 对象变更的下游影响已检查
- 稳定 ID、引用和状态经确定性 lint 校验
