# 集成契约建模
> 将跨系统交互建成带边界、负载、键、失败语义、安全和对账的可评审候选契约

## 何时用
解决方案涉及 API、事件、文件、批处理、ETL 或人工交接，需明确生产方、消费方、
数据与运行语义时使用；仅列一个接口名或产品功能不等于已建立集成契约

## 步骤
1. 对每条集成先定义业务目的、需求 ID、生产组件、消费组件、主数据所有权、
   触发和方向。同一系统自循环或所有者不明时先形成问题。
2. 用 `oir.query` 校验系统、DataObject、Event、Action 和 requirement 引用；候选组件或
   contract 可使用方案本地稳定 ID，但不得冒充已存在客户系统 ID。
3. 用 `evidence.search` 和 `evidence.rows` 核对交互模式、协议、方向、频率、网络边界和
   客户已有中间件；无证据的具体产品、端点和版本保持 UNKNOWN/null。
4. 定义 payload 中的业务对象 ID、主键/关联键、必填、单位、币种、时区、编码和
   schema 版本。`profile.column` 只验证分布、完整性和唯一性，不证明业务键语义。
5. 分别记录身份验证、授权、敏感等级、加密、数据最小化和审计要求；不把“内网”
   等同于已安全。
6. 定义幂等键、重复语义、排序、超时、重试、死信/补偿、部分失败、人工介入和
   回放方式；“失败后重试”不是可验收契约。
7. 定义业务与技术对账、可观测信号、SLA/SLO、数据新鲜度、告警与责任角色；缺失
   的可测量目标形成问题，不自行编造数字。
8. 用 `impact.trace` 检查契约变更的上下游影响，用 `model.lint` 检查 ID、引用和结构；
   输出仅是候选方案，不声称接口已开发、连通或上线。

## 完成判据
- 每条契约都有业务目的、requirement ID、生产方和消费方
- 触发、模式、方向、payload 对象和关联键已明确或保持 UNKNOWN
- 身份验证、授权、敏感性、加密和审计约束已记录或已提问
- 幂等、重试、超时、部分失败、补偿和回放语义可验收
- 对账、可观测性、SLA/SLO 和责任角色有可测量定义或明确缺口
- 契约是候选方案，没有声称已开发、连通、上线或获批
