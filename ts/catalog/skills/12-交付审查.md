# 交付审查
> 作为独立质量门验证结构化产物、证据、决策、风险和下载包的一致性，阻断项未清零不得放行

## 何时用
准备向 FDE、业务负责人、ERP 顾问或下游系统发布阶段产物时使用；不用于补写业务
事实，也不替代业务方回传模板审核

## 步骤
1. 先读取已有确定性检查结果；缺失时运行 `model.lint` 检查 JSON Schema、稳定 ID、
   唯一性、引用完整性、悬空边、状态和流程可达性。确定性失败直接进入 blocker。
2. 用 `oir.query` 和 `impact.trace` 做双向追溯：流程步骤 ↔ Action/Event/DataObject/
   Rule/ERP mapping ↔ evidence。记录 `traceability.checked` 和 unresolved 明细，
   不使用“基本完整”。
3. 检查可视化与结构化输出的节点数、边数和 ID 是否一致；图只能是结构化模型的派生物。
4. 按风险抽样核验证据定位、来源版本和原文含义，确认事实、推断、UNKNOWN、已回答、
   已延期和风险没有混写。
5. 检查决策记录包含决策人、时间、原问题、回答、证据、影响范围和被取代版本。
   当前 schema 无 accepted-risk 字段：已有明确批准的风险写入 `warnings` 字符串，
   包含批准人和到期条件；未批准或会破坏质量门的风险必须成为 blocker。
6. 检查交付 manifest、版本、必需文件、可打开性、可下载性、敏感数据暴露、已知限制
   和复现信息。`artifact_checks` 只填写 schema 支持的字段，其他失败写入 blocker
   message 或 warnings，不新增字段。
7. 每个 blocker 使用稳定 code，message 中写明证据和修复条件，并填写 owner role
   与 artifact IDs；Reviewer 不直接修改被审查产物。
8. 只有 blockers 为空、必需产物可下载、Schema 合法且追溯门槛满足时判 `PASS`，
   否则判 `BLOCKED`。

## 完成判据
- Schema、稳定 ID、引用和流程可达性检查已完成
- 跨产物追溯给出 checked 数量和 unresolved 明细
- 可视化与结构化输出的数量和 ID 一致
- 事实、推断、未知、延期和风险没有混写
- 每个 blocker 都有代码、责任角色、影响产物，message 包含修复条件
- 交付 manifest、版本、安全性、可打开和可下载已检查或形成 blocker/warning
- blockers 未清零时没有判 PASS
- 输出严格遵循 delivery_reviewer schema，审查过程中没有直接修改被审产物
