# 证据治理
> 把来源、版本、定位和主张绑定成可复核的证据链，避免搜索命中和行业常识被当成客户事实

## 何时用
材料来源多、版本不一、引用粒度过粗，或下游要求、流程、方案和测试需要
建立主张到原文的双向追溯时使用；不用于替代业务裁决或把外部搜索结果升格为客户配置事实

## 步骤
1. 盘点当前任务可见的材料、证据 ID、原文定位、来源版本、生效范围和时间。
   只有文件名、搜索摘要或二手转述时，不得标记为已核验原文。
2. 用 `evidence.search` 定位候选，再用 `evidence.rows` 读取包含标题、表头、上下文和
   例外的最小足够片段；搜索为空只表示未命中，不证明材料中不存在。
3. 将每条输出主张分为 `FACT`、`ASSUMPTION` 或 `UNKNOWN`。`FACT` 必须绑定能
   直接支持该表述的 evidence ID；推导结论不得沿用原文的事实标签。
4. 为关键主张建立“主张 → 证据 → 来源定位”和“证据 → 使用主张”对应；用
   `oir.query` 核对当前 OIR 中的稳定 ID，不把 OIR 模型值倒置为原始证据。
5. 检查版本、组织、地区、时间、币种、单位、税口径和适用对象。同名条款来自
   不同范围时并列保留，不静默覆盖。
6. 两条证据冲突时，同时保留两方原文、定位和冲突轴；权威性可作排序线索，
   但没有明确决策权和适用范围时不自行选择赢家。
7. 对缺失定位、过期版本、无法打开、仅有抽样或语义不足的证据形成问题或
   缺口，写明所需原件、应答角色和被阻塞产物。

## 完成判据
- 每条 FACT 都能点回真实存在的 evidence ID 和精确定位
- 搜索摘要、推断和 OIR 模型值没有被当成原始证据
- 版本、适用范围和时间已检查，旧版本没有静默覆盖新版本
- 冲突证据同时保留两方原文与冲突轴
- 关键主张具有双向追溯，不存在无主张的装饰性引用
- 无法核验的证据已按当前 schema 进入 question、gap 或 unresolved 字段

evidence.search、evidence.rows、oir.query
